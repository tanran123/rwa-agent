Execution Map

Agent 执行链路

页面说一句话，Koa 原样转给 Flask，DeepAgents 决定调哪个工具，计算流水线按固定顺序干活。下面五张时序图，把每条链路拆开讲清楚。

先记一句口诀：前端点菜，Koa 传菜，Flask 是后厨总管，DeepAgents 是厨师长，tools 是专用工具，calculation 是固定流水线，output 是出餐口。

A

右下角 AI：一次对话

顾客点菜，前台传话，后厨总管叫记录员，厨师长决定用哪个工具。

一句话：Koa 不做智能体，只做传菜；真正的对话在 Flask 里由 client.reply 和 DeepAgents 完成。

  1. 顾客递单子。
    页面把当前页面、最近几句话、上一轮的 threadId、是否确认、页面有哪些表单打包发出。
  2. 前台原样转。
    Koa 的 /api/agent/chat 只做转发，所以 Koa 里没有智能体逻辑。
  3. 总管叫记录员。
    Flask 调 composition/client.py 的 reply()，由它负责裁剪、续接和成形。
  4. 记录员先整理。
    只留最近 8 句、每句最多 800 字；找到这桌的档案；看看上次是不是停在“确认算吗”。
  5. 交给厨师长。
    DeepAgents 先看技能目录，只给名字和一句话；需要时再让帮厨去档案柜取正文。
  6. 工具循环。
    查进度用 pipeline_steps，要算用 run_weight_decision，填页面用 page_actions。
  7. 端一整盘出来。
    记录员整理成 reply / pages / draft / actions / threadId / confirm 六个字段，页面再渲染。
A2

确认分支：先拦住，再开算

算一本底稿可能几十秒，不能模型一冲动就开算。

一句话：interrupt_on 像门口保安，工具一被调用先暂停，只有页面点确认才放行。

页面看到的固定文案是“将计算工作簿：xxx。确认后才会开始计算。”这句话由中断请求里的 action_requests 拼出来。
B

计算流水线：只开一个工位

确认后，工作簿被放上一条固定工序的传送带。

一句话：模型只负责按下“开始算”；走哪一步、按什么顺序，全由 registry 和 calculation/graph.py 决定。

  1. 按下按钮。
    模型调用 run_weight_decision，确认通过后进入 run_pipeline。
  2. 检查文件。
    路径在不在、是不是 .xlsx/.xlsm、weight 在不在名单里。任何一条不对，直接返回一句话。
  3. 开传送带。
    把工作簿路径、结果路径、已跑步骤记进状态，线程号是父对话加 ::calculation。
  4. 看工位牌。
    registry 回答只有 weight 开着，所以传送带不会把活送到 ccf、crm、rwa。
  5. 老师傅开工。
    选表、读表、对列、拆笔、合并债务人、定评级、补空白、查规则算钱。
  6. 写档案。
    逐笔留痕写 output/traces/，结果工作簿写 output/workbooks/ 或上传文件旁边。
  7. 交回结果。
    敞口和 RWA 只从 run_workbook 的返回值抄，不在工位里重算。
后三个工位挂着“暂未启用”的牌子。就算有人硬把活送过去，它们的 run 也只会写“还没实现，停住”，不会编一个系数或金额。
C

计量向导：另一扇门

这条链路不经过 Flask，Koa 直接对讲机喊 Python 师傅。

一句话：同一个引擎，走的是另一扇门；所以别在 Flask 里找它。

  1. 页面点“映射”。
    请求发给 Koa 的 /api/measure/map。
  2. Koa 自己喊人。
    measure.js 用 spawn 起一个 .venv/bin/python -c ...。
  3. Python 调引擎。
    import 的是 agent/steps/weight/calc/model.py，调用 suggest_standard_fields。
  4. 原路返回。
    结果回到 Koa，再回页面；Flask 完全不参与。
D

HQLA 七步：前台管档案，后厨判卷

任务、明细、参考库都在 MySQL；Flask 只负责按规则判卷。

一句话：这条链路全程不调用模型，匹配靠归一化后的 组合|代码。

  1. 页面点计算。
    请求发给 Koa 的 /hqla/tasks/:id/compute。
  2. Koa 翻档案柜。
    从 MySQL 取出任务、逐笔明细、内部清单和外部参考库。
  3. 交给后厨判卷。
    Koa 把这一包发给 Flask 的 /api/hqla/compute。
  4. 逐笔走规则。
    service.compute 调 judge.run，再汇总、算上限、和申报数对账。
  5. 结果原路回。
    逐笔、统计、汇总、上限、对账一起回到页面。
  6. 取数日志和导出。
    第 5 步日志由 Koa 写回 MySQL；导出 Excel 再由 Koa 请 Flask 生成。
E

两条旁路：底稿、决策树

这两条不参与右下角对话，但都在用同一套引擎或同一份数据。

一句话：底稿页直接翻账本，决策树只改草稿。

底稿页

直接翻账本

Koa 只读 底稿模型计算.json，分页、改字段名。页面看到的数和文件里一致，不重新算。

决策树

顾问只改草稿

模型返回“改哪几个节点”的 JSON，不落笔。保存、版本、复制仍然由 Koa 做。

!

三个容易混淆的点

记住这三条，基本不会把链路的责任搞错。

01

入口不是实现

llm/graph.py 只是入口，实际图在 llm/agents/chat.py。

02

计算顺序不由模型决定

模型只按“开始算”的按钮；走哪一步、什么顺序，由 registry 和 calculation/graph.py 固定。

03

工具名单只有一份

右下角 AI 读 agent/tools/__init__.py；新增工具只改这一处。

对应代码：agent/llm/、agent/llm/session/、agent/core/pipeline/、agent/steps/、agent/tools/。 图中的端口 8780 是 Koa，8766 是 Flask。
